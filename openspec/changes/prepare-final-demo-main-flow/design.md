# Design: prepare-final-demo-main-flow

## 演示叙事（核心）

评委打开 `home.yueming.xin` 看到一个正常运行的轻量业务页面（订单/查询），
并在同一页面点击“注入连接池故障”。该控制台动作调用 OpsKeeper Manager 的
演示场景 API，由 Manager 编排 pool-fixture 并生成 incident_id。
随后订单、库存、审计等数据库依赖区域请求变慢 / 部分失败，而静态导航与页面壳保持
可用，让评委从**业务体感**发现问题。演示者切换到监控页确认连接池 4/4、等待队列
与应用错误率上升；此时 Prometheus 告警已自动进入 OpsKeeper。观众再切到 Element
房间查看 Manager 主持诊断、预演与修复建议。人工审批后执行修复，先在监控页确认
连接池容量与占用恢复，再回到 home 重新查询订单 / 库存 / 审计数据，确认业务恢复。

**关键**：home.yueming.xin 不只是展示页，它是"故障体感放大器"——
让评委看到连接池耗尽如何影响真实业务，而不是只看 PG 内部指标。

### home 控制台的注入边界

- home **不直接连接 pool-fixture，也不持有数据库或负载凭据**；它只调用 Manager 的
  `/demo/scenarios/pg-pool-exhausted/start` 类受控 API。
- Manager 负责场景白名单、目标指纹、影响面、持续时间、幂等键和 incident_id 生成；
  重复点击返回同一 incident，不重复注入。
- 注入成功后，Manager 发送 `agentteams.workflow` 事件并让 home 进入进度看板。
- Prometheus 告警仍然独立触发；告警与控制台动作通过同一 alert_fingerprint /
  incident_id 关联，避免 home 绕过监控链路。
- 路演者不需要在 Element 中复制“故障注入”提示词；房间提示词仅保留为回调失败时的
  演示兜底，并必须走同一个 Manager 入口。

## 评委建议二的满足方案（不用 PolarDB HA）

结构化预演记录、PASS/FAIL 门禁和 Archive readback 以 `repair-preview-readback`
能力为准；本变更消费其 API 与插件展示，不另建第二套预演事实源。路演时在人工
审批前展示紧凑的 baseline / Candidate A / Candidate B 决策证据；完整对比表在
事故关闭后的 Archive 中回看。

### 已有基础

当前 `preview-pg` 页面（`http://8.160.172.235:13001/preview/`）已实现：

| 能力 | 当前实现 | 对应评委建议 |
| --- | --- | --- |
| 修复预演 | 独立 Docker PG 16，固定负载重放，checksum 校验 | "在数据库分支中预演修复" |
| 候选对比表 | Baseline vs 候选A（索引）vs 候选B（数据修复），展示延迟/TPS/checksum/一致性/存储影响 | "对比结果一致性、查询延迟和写入影响" |
| 一通过一拒绝 | 候选A 通过 → 进入 HITL；候选B 数据丢失 → 拒绝 | "一个修复方案经过实测后被批准，另一个因验证失败被拒绝" |
| 事故档案反查 | 按 incident_id 关联 7 阶段事件/执行者/证据引用/Trace | "建立完整的事故数据档案" |
| 控制面隔离 | 控制面 DB / 被运维目标 / preview-pg 使用不同容器/volume/网络 | "控制面数据库与被运维目标分开部署" |
| 备份恢复 | 每日备份保留 7 天 + 恢复到临时库行数校验 | "备份恢复" |
| 诚实边界 | "preview-pg 只重放固定负载，不复制原实例活动会话" | "锁等待、连接池耗尽需要重新构造受控负载" |

### 需要增强（连接池耗尽主案例的对比）

**问题**：当前对比表只覆盖数据层修复（索引/数据修复），主案例"连接池耗尽"是运行态问题，不能直接在 preview-pg 分支上复制。

**方案**：三层对比框架。设计上区分两类证据：`home.yueming.xin` 在真实事故中的
故障前后表现是**业务观测证据**，用于说明影响与恢复；`preview-pg` 上的相同负载
重放是**修复决策证据**，用于比较候选方案。两者不能互相替代，也不能把受控重放
表述为生产活动会话的完整复制。

所有预演必须携带同一个 `replay_profile_id`：固定负载模型、并发数、持续时间、
SQL 分布、超时时间、随机种子、目标版本与修复版本。缺少该标识或配置不一致时，
对比表显示 `NOT COMPARABLE`，不进入审批结论。

#### 层1 — 业务体感对比（home.yueming.xin）

在 home 页增加一个"故障前后对比面板"：

```
┌──────────────────────────────────────────────────┐
│  PG 连接池耗尽 — 业务影响对比                       │
├──────────────────┬───────────────────────────────┤
│  故障期间          │  修复后                         │
├──────────────────┼───────────────────────────────┤
│  请求延迟: 3000ms+│  请求延迟: <50ms               │
│  成功率:   ~60%   │  成功率:   100%                 │
│  连接池:   4/4 满 │  连接池:   0/8 空闲             │
│  页面状态: ⚠️ 慢  │  页面状态: ✅ 正常               │
└──────────────────┴───────────────────────────────┘
```

- 数据来源：pool-fixture API + home 页自身的请求埋点
- 修复后持续采集 ≥30s，避免"单次探针成功"即代表恢复
- 这层给评委**可感知的对比**，弥补数据库内部指标不够直观的问题

**实现要求**：三张数据卡片不能由浏览器直连数据库，也不能使用静态假数据。新增一个
轻量业务查询层，服务端持有连接池和数据库凭据；订单、库存、审计分别暴露独立 HTTP
查询端点，并执行不同 SQL / 数据视图。前端每个卡片独立请求、显示独立延迟与错误态，
设置 1～2 秒客户端超时，响应禁止缓存。故障注入必须作用于该业务查询层的同一个应用
连接池；修复后仍通过同一路径重新查询，证明业务恢复而不是切换了备用通道。

短期可将该查询层并入现有 pool-fixture 进程，复用其已饱和的 PostgreSQL pool；
更清晰的长期形态是独立 `home-app` 服务，并将业务库与 OpsKeeper 控制面库分离。

#### 层2 — 运行态重放对比（preview-pg + pool-fixture）

在 preview-pg 上用受控负载重演连接池耗尽，对比修复前后：

```
步骤：
1. 在 preview-pg 上启动 pool-fixture（饱和连接）
2. 记录 baseline：active=4/cap=4, probe_latency=500ms, error_rate=40%
3. 应用修复（如 pool resize 4→8 / connection recycling）
4. 相同负载下重放
5. 记录 candidate：active=0/cap=8, probe_latency<10ms, error_rate=0%
```

- 关键：**同一受控负载，同一预演环境，唯一变量是修复方案**
- 这层给评委**定量的运行态对比**，说明修复方案经过实测验证
- 诚实声明：重放负载 ≠ 生产会话完整复制（页面已标注）
- 候选一：`pool resize + connection recycling`，要求延迟 / 错误率 / 池占用达标且数据 checksum 一致
- 候选二：`aggressive restart / kill sessions`，若造成请求中断、状态漂移或违反影响面约束则拒绝
- 结论只写“在受控重放中通过/失败”，不写“等价于生产必现”

#### 层3 — 数据层回归校验（preview-pg）

在修复前后各跑一次 checksum 校验，确认连接池修复不引入数据问题：

```
修复前 checksum: 28c182bd...
修复后 checksum: 28c182bd...  → PASS（数据一致）
```

- 防止"修好了连接池但弄坏了数据"
- 这层与现有的候选A/B对比表共用基础设施

### 三层组合满足评委建议二

| 评委要求 | 层1（业务体感）| 层2（运行态重放）| 层3（数据回归）|
| --- | --- | --- | --- |
| 对比结果一致性 | — | — | ✅ checksum |
| 查询延迟对比 | ✅ 页面请求延迟 | ✅ probe latency | ✅ 固定负载延迟 |
| 写入影响 | — | ✅ error rate | ✅ TPS + 存储 |
| 修复前实测 | ✅ 页面体感 | ✅ 受控负载 baseline | ✅ 数据 baseline |
| 修复方案一通过一拒绝 | — | ✅ pool resize vs aggressive kill | ✅ 候选B 数据丢失拒绝 |
| 不复制活动会话 | — | ✅ 诚实标注 | — |

### 单机 Docker 下满足建议二的可靠性增强

不引入 PolarDB HA 时，项目用“隔离 + 持久化 + 可恢复 + 幂等”回应可靠性要求，
但不宣称具备自动 failover：

1. **控制面独立**：OpsKeeper 控制面数据库、被运维 PG、preview-pg、业务 demo 页面分别使用独立容器 / volume / 网络。
2. **状态持久化**：告警、诊断证据、候选预演、审批等待、执行状态、验证结果全部按 incident_id 落库。
3. **重启留存演示**：在待审批或待验证状态重启 OpsKeeper Manager，刷新后事故与审批进度仍存在。
4. **幂等保护**：修复请求携带执行 ID 与目标指纹；重试或重启后先 readback 状态，目标指纹不一致则拒绝执行，避免重复修复。
5. **恢复演练**：控制面数据库每日备份，并保留一次“恢复到临时库 + 行数 / checksum 校验”的演示记录。
6. **诚实边界**：这是单机 Docker 可靠性增强；生产演进路径为托管 PostgreSQL / PolarDB 高可用与跨可用区备份，不作为当前决赛演示能力宣称。

## 决策

### D1: 主案例唯一化
按评委建议，主案例固定为 PostgreSQL 应用连接池耗尽。错误目标拒绝作为同一案例内的转折点。CPU 等保留为答辩备选。

### D2: 房间绑定
`#benyue-lumos-ops:matrix-local.agentteams.io`。Dashboard 集成自检 warn（Manager 矩阵账号持有房间）为预期。

### D3: 入口分层
- **home.yueming.xin** — 路演开场 + 业务体感 + 恢复确认（评委第一眼看到的页面）
- **监控页** — 注入后确认连接池 4/4、等待队列与应用错误率；修复后确认容量与占用恢复
- **teams.yueming.xin** — Dashboard 任务看板 + Runtime + 归档（演示过程中切换）
- **rooms.yueming.xin** — Element 房间对话（展示 Manager 派发/审批/执行消息）
- **preview（内嵌链接）** — 修复预演对比表（演示"修复前先测过"的证据）

### D4: 可观测指标
- home 页面：请求延迟 / 成功率 / 页面状态指示器
- Runtime 页：修复后 ≥30s 持续观测窗口（连接池 / 请求指标）
- 归档页：evidence_complete=true + 全部 trace_id 可反查

### D5: 不用 PolarDB HA 的边界
- **已做**：控制面 DB 独立容器 + 每日备份 + preview-pg 隔离
- **不做**：双节点 HA / 自动 failover / 跨可用区
- **诚实表达**：在 PPT 和页面标注"单机 Docker 可靠性增强；生产演进路径为托管 PolarDB PostgreSQL 高可用"
- **已满足**：评委建议二的三个子项（档案/预演对比/控制面可靠）在单机 Docker 下均有对应证据

## 数据流

```
[开场] 评委打开 home.yueming.xin → 页面正常，请求 <100ms
   ↓
[触发] home 控制台一键注入 → Manager 编排 pool-fixture → 连接池 4/4 饱和
   ↓
[体感] home 页面请求变慢/失败 → 评委看到业务受影响
   ↓
[监控] 演示者切换监控页 → 确认连接池 4/4、等待队列与应用错误率
   ↓
[告警] Prometheus 检测 pool_exhausted → opskeeper-alerter 触发
   ↓
[诊断] opskeeper-investigator 只读查询 pg_stat_activity / pool metrics
   ↓
[预演] Manager 在 preview-pg 上重放受控负载 → 对比修复前后指标
   ↓
[提案] opskeeper-reviewer 生成修复方案（目标/参数/范围）
   ↓
[审批] Element 房间推送审批卡片 → 人工批准（绑定目标+凭据）
   ↓
[转折] 展示错误目标被拒绝（安全约束生效）
   ↓
[修复] opskeeper-repairer 执行 pool resize / recycling
   ↓
[验证] opskeeper-verifier 连续 30s 观测 → 监控确认池恢复
   ↓
[复查] 回到 home 重新查询订单/库存/审计 → 数据正常返回
   ↓
[关闭] Manager 关闭事故 → opskeeper-reporter 生成复盘
   ↓
[回看] Dashboard 归档页 evidence_complete=true → trace 可反查
```
